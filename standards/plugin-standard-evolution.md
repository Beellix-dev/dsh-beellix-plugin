# 插件标准的持续维护

本目录是 Beelli X 生态规范的维护根。当前标准1.1.0，1.0.0是首轮基线；继续根据真实插件、用户使用和DSH兼容情况完善，不作为“全部成熟”的承诺。

2026-10-28企业场景按用户要求各自独立初始化，澄清“复用程序”与“复用数据”不同。业务描述v1的可选engine.storage=scene要求场景PostgreSQL、必需数据库SDK及运行时隔离工厂；原描述省略时保持provider规则。新描述须使用本次检查器，不回写旧描述／库或自动迁移绑定，数据契约、标准和包版本保持；实施与证据沿独立数据库方案。

2026-10-28公众生态补充形成评审基线：[十二类适配与准入要求](ecosystem-conformance.md)与[共同任务／验收格式](plugin-development-task.md)，用于人工、Codex及DSH创造模式。尚未调整机器Schema、运行契约或标准版本，不代表第三方安装、任务调度或公网发行已开放；字段及行为落实时按兼容规则正式发布，不能悄悄放宽安装范围。

同日进销存／CRM审计补充[跨插件互通与授权](cross-plugin-integration.md)I01—I12及X01—X08：将单应用隔离之外的可信身份、字段／动作授权、对象映射、幂等交付和恢复列为明确门禁。它仍是协议设计，未添加通用互通服务；标准版本、现行Schema及自有包版本不变，不能以新增文档声称业务已互通。

## 每次完善的顺序

1. 从实际插件或使用问题提出改动，写清适用类型、现有缺口、验证方式。
2. 先查已有 DSH 能力和 Beelli X 公共契约；通用规则放主标准，场景、工具、技能、能力包差异放相应接入规则，不让每个插件重复实现中台。
3. 声明、文档、校验器、技能指引、样例与行为测试同步修改。设计中、已实现、已验证、已采用分别记录。
4. 以有代表性的真实插件验证安装、执行、隔离、升级、停用和恢复；先用隔离环境，日常采用单独确认范围。示例和静态检查不替代完整应用验收。
5. 固定候选包摘要，再分发到创造模式；保留旧契约兼容及明确迁移办法，不静默改写已有工程、会话或业务资料。

包版本、标准版本、工程 Schema 和业务数据版本分别管理。自有包当前保持0.1.1，只按用户要求更新。文档澄清不自动改变协议版本；字段或行为兼容性改变时同步处理版本、校验和迁移。已分发快照按包摘要识别，不用同一版本号推断内容相同或已经部署。

标准的补充规则与兼容扩展用次版本；不兼容变更须新主版本和显式迁移方案，纯澄清不强制改变工程版本。当前接受的标准由工程Schema列出；检查器、快照、Skill与主文档保持一致。新增校验只作用于明确声明新标准的描述，不把旧工程检查结果悄悄改成新标准就绪。规则能静态验证的接检查器，视觉、权限、模型质量和真实依赖等仍记录对应人工或运行验收，不能用文本匹配假装已测。

兼容方向是新检查器读取旧描述，不承诺旧检查器理解1.1.0新描述。不要为适配旧包而改写工程版本或首次启用时间；采用与回退使用对应包快照，未确认的降级明确停止并保留原件。

## 接下来逐项验证

| 方向 | 当前缺口与完成依据 |
| --- | --- |
| 创造模式闭环 | 尚未执行真实模型自主开发任务；先完成一个最小工具包的开发、检查、隔离试装和实际调用 |
| 场景和数据库 | 工程登记、业务账套首次初始化、运行依赖门禁和迁移协调尚需完善；用独立样板验证，不转换现有报价资料 |
| 知识与数据中台 | 知识已有独立实现，按所装提供方、契约、features、权限和状态接入；数据中台仍待交付，不预造 API |
| 模型与分发 | 用实际包声明验证专用模型和更新链路；网站、可信签名与受控下载未完成前不开放为正式公网能力 |
| UI及其他包类型 | 按真实业务补充运行身份与接入边界，不提前硬编码所有分类 |
| DSH兼容与交付 | 针对明确的官方版本验证四模式、权限、上下文、子代理与插件生命周期；再形成兼容结论 |

这些是演进方向，不表示已自动排期、启动开发或完成交付。

## 目录卫生

活动源码、有效测试、规范和必要工具保留。dist 只保留当前采用的发行包；未采用候选及其必要证据集中在 .artifacts 的当前任务目录。重复安装包、旧解包副本和可重建临时环境应在验收后清理。

清理先核对路径、引用和运行进程；拒绝意外目录和重解析点，不删除真实业务、凭据、备份或恢复链。保存一份当前清理回执，不逐次堆积重复版本日志。构建成功不等于可以删除唯一可复现的已采用基线。
