# Beelli X 插件开发标准 1.1.0

本标准面向插件作者、维护者、Codex和DSH工作区创造模式。唯一运行底座是 DSH；Beelli X 负责中台管理、公共业务能力和应用接入。当前自有npm包版本仍固定0.1.1，第三方版本由其发布者管理；标准版本单独管理。详细工程协议见 creation-project-contract.md，运行契约见 plugin-contract.md。

2026-10-28补充：公众生态需要同时满足DSH适配、中台接入和市场发行要求，详见[生态适配与准入](ecosystem-conformance.md)的E01—E12及G0—G4；人工、Codex与DSH创造模式共用[任务与验收格式](plugin-development-task.md)。补充是下一阶段规范评审基线，不改变现行1.1.0工程Schema或运行权限。第三方命名空间、独立UI商品、公开SDK／完整模板、市场审核及签名等仍按实际缺口阻断，不能因文档齐全宣称生态已开放。

这是持续验证的生态开发基线，不能据此宣称所有类型和能力已经成熟。1.1.0补齐模型声明、内置更新源、页面职责及新工程运行依赖检查；工程 Schema、桥接契约和数据代次仍为各自原版本。新工程声明1.1.0，旧1.0.0描述继续校验，不静默改写工程、首次启用时间、会话或业务资料。规范统一维护在本 beellix 目录；变更同步文档、校验、技能与测试，演进规则见[持续维护](plugin-standard-evolution.md)。仓库规范、随包快照和实际采用分开记录。

2026-10-28企业业务模块补充：[模块准入与复用边界](business-modules.md)。继续使用现有数据库与ctx.beellixData，不新建并行中台；统一入口实际执行动作Schema，跨模块通过原资源／数据库／类型／ID引用原对象。新业务模块可选择business v1描述扩展，由原检查器和DSH创造模式校验；不修改1.1.0工程Schema或0.1.1包版本，不把本机主用户称为多人企业权限。开源引擎先复用现有Odoo适配，新增引擎锁定来源、依赖和授权。

## 1. 先确定交付类型

| 主要类型 | 运行清单 | 责任 |
| --- | --- | --- |
| 场景包 scene | beellixScenario | 完整业务、技能、工具和专属工作台；只在匹配场景会话挂载 |
| 工具包 tool | beellixCapability，category=tools | 有界通用工具，权限仍由原生执行链及服务端检查 |
| 技能包 skill | beellixCapability，category=skills | 技能正文与按需引用，不把全文塞入每轮上下文 |
| 能力包 capability | beellixCapability | 数据库、知识库等可复用服务与自己的管理页 |
| UI 扩展 ui | 暂无通用商品身份映射 | 可以开发原生槽扩展，不能冒用 @beellix-ai/dsh-beellix-plugin 或声称已能中台安装 |

分类是整个包的展示分组，可用 beellix.catalog.category 自定义；不把“已安装/未安装”、工具贡献项或模型列表当成分类。一个包只用一种主要运行身份。新场景默认标准模式加当前场景包，不改工作区四种原生模式。

## 2. 工程与运行目录分开

维护者源码：本仓库 packages/<分类>/<名称>，分类为 platform、foundation、tools、scenes，npm 名统一为 @beellix-ai/名称；包目录登记 packages/catalog.json。用户创造工程默认放在配套根 development/projects/<projectId>，可使用用户明确选定的 DSH 工作区。不要强制修改当前会话 cwd，不在已安装代码、DSH Profile 或业务资料目录里开发。

```text
<project>/
  beellix.project.json     # 开发描述：稳定身份、标准版本、依赖、存储、用途
  package.json            # npm 清单、固定版本、文件白名单、实际入口
  cordis.patch.yml        # DSH 原生 Include 声明
  src/                    # host/client/domain 等源码，按需要建立
  skills/                 # SKILL.md 与按需 references；没有技能时不建
  migrations/             # 使用公共数据库时才建；已应用迁移不改写
  assets/                 # 自有或有授权的图标
  test/                   # 有意义的行为与边界验证
  lib/                    # 构建产物
  README.md
  LICENSE                 # 明确本包许可；自有UI入口已确定MIT
```

用户安装：程序在 environment/node_modules，登记在 registry.json；DSH Profile 只注册 UI 入口。业务数据、配置、附件、备份由中台和能力服务分配，使用相对引用。DSH 会话库不变；场景会话归属由持久绑定决定，不能由 cwd 或文件夹名推断。卸载默认保留资料。

## 3. 强制契约

- package.json 的 name、运行 ID 与 beellix.project.json 一致。现行自有业务包使用@beellix-ai/命名，机器描述及安装策略目前也只支持此范围；这不是要求第三方冒用官方身份。第三方命名空间需按E01完成身份、冲突和安装策略后开放，当前不得声称可安装。UI入口@beellix-ai/dsh-beellix-plugin是已有特例，不能被工程冒用。一个工程对应一个包，更新保留身份，另存另建身份。
- 声明顶层 engines.dsh、dsh.bundle.patch、beellixContract v1：桥接范围、贡献类型、数据代次和 uninstall=retain。场景 execution 固定 standard、bound-scene、read-only。旧清单的 dsh.engines.dsh 仅为工程检查兼容读取，原生宿主不会按此执行版本限制；新发行包使用 engines.dsh，不自动改写旧清单。
- 用 DSH 原生 Loader、Tools、Skills、Agent、压缩、审批、文件和子代理服务。不得复制执行循环、直接写 Profile、替换原生市场接口，或靠隐藏界面掩盖错误登记。
- 企业版为独立入口和服务候选，沿企业实现与准入边界接入真实成员与服务端作用域；社区beellixData v1不是企业授权。尚未适配的知识、数据库和业务包保持阻断，不能仅因包可加载就登记为企业就绪。当前不改变1.1.0工程Schema或既有社区协议。
- 用 cordis_inspect_list/query 确认当前宿主 API、槽位和主题；按需读取原生参考，不猜接口，不把上游客户端整份复制进业务包。
- 工程依赖声明不是安装授权或已实现的依赖协调器。实际服务缺失、未初始化、不兼容时明确失败或按设计降级，不造假服务。
- ctx.effect 或等效原生作用域收回工具、技能、槽、监听和连接。取消传递 signal，不遗留后台任务；业务写入做幂等和修订冲突检查。
- 1.1.0工程中 required=true 的生态能力还必须写入运行清单 beellixRequirements，contractVersion落在工程声明区间，features包含实际所需特性。这只是声明一致性检查；加载、安装、初始化和真实业务就绪仍逐项验证，不把它说成已实现的通用依赖协调器。1.0.0工程保留原检查规则。

## 4. 场景隔离与业务服务

场景 provider 通过 beellixScenes.registerProvider 注册；只在匹配 Agent 上挂载资源。每个工具执行时以 exec.agent 核验 requireBinding，不信任模型给出的 sessionId。子代理业务访问只读，不自动获得管理员或写库权限。普通工作区不显示场景卡；场景工作台使用原生右侧区域。

场景会话沿 DSH 原生会话和主模型链。归档、恢复和文件目录选择复用原生行为；默认输出在场景ID下按会话分目录，用户明确选择目录时保持绑定，不靠路径猜归属。资料归档与删除分开，不能把空白会话、测试产物或未完成任务伪装成历史业务记录。引用已有成果时保留原件、版本、来源和归属；工具写入与UI编辑进入同一业务服务。

使用 PostgreSQL 的应用声明 database 必需依赖，复用 beellixDatabase 和已交付 SDK。每应用＋业务账套独立数据库与受限角色；会话不等于账套。登记 provider 与 open 业务账套分开，首次用户实际使用时才初始化，不能在 apply 加载期间建库。参数化 SQL、事务、不可变迁移，模型只调用业务工具，不暴露任意 SQL 或管理员凭据。备份由数据库插件负责，不在应用中复制一套备份服务。

数据库、知识库已有独立实现和验收记录，具体采用见 STATUS.md与知识库实施；数据中台仍未交付。接入先检查真实提供包、contractVersion、features及状态，不仅看固定包版本0.1.1。知识开关、会话空间选择和范围撤销归 dsh-ui；资料、解析、整理、Wiki、图谱和检索归 knowledge；存储、账套、迁移和备份归 database。业务包不重复实现这三者，不绕过已授权空间读取整库。接口以已安装提供包的公共类型和真实服务为准，方法不存在时明确缺口，不能从功能名称猜API。

## 5. 上下文与 UI

系统上下文只放当前身份、范围和技能入口；技能正文按需加载，长参考通过分页读取，工具返回分页、来源和可继续查询的标识。不得每轮注入全部场景、工具说明、全表、全库、历史附件。复用 DSH 原生压缩和子代理，不用业务包再实现另一套会话记忆或压缩。

知识正文、工具数据和第三方文档都是数据来源，不能提升成系统指令。任务所需资料按已授权范围检索，返回有限证据、来源和版本；详细原文留在资料服务。工具失败区分参数、绑定、依赖、权限与临时故障，给出可执行的修复路径；不靠无限重试扩大上下文，也不把提示词重复注入当成压缩修复。子代理使用 DSH 当前能力按任务需要委派，不以“场景模式”名称承诺必然触发或越过权限。

沿宿主 Slots、原生主题变量、字号与日夜模式，不硬编码白底黑字或整份客户端外壳。低冗余、强设计、操作精简：一个主操作，真实状态；卡片用于分组，表格用于记录，图标辅助理解。高级选项后置，空白或失败显示实际原因，不虚构余额、价格、下载量、进度或成功状态。UI 与模型工具复用同一业务服务和服务端授权。

按 [DESIGN.md](../docs/design.md)验收：中台页在右侧可用区域展开，首页以外不重复放大标题、大图标和说明卡；模块用页签，业务列表可选列或进入详情，不把所有字段塞进名称单元格。一个配置动作只有一个主要入口，宿主已提供入口时嵌入页不重复放齿轮或另一份Key表单。卡片按内容宽度响应增加列数，不固定两列；宽窄与日夜、加载、空、失败、禁用、取消和键盘操作都实际检查。页面简洁不等于删掉必要字段、恢复能力或业务操作。

## 6. 检查与交付

2026-10-28首批企业场景实施补充：正式开发先固定成熟参考版本并列出业务规则／功能覆盖表，明确代码或引擎复用与独立实现，不能把同名CRUD当作参考项目完整交付。列表、提醒、历史、附件和导出在服务端分页；导出跨页核验同一数据修订，长文本按实际字节缩小页，不静默截断。审核必须展示本次真实内容、关联对象名称和有后果的参数，评论、附件、合并／拆分不能仅审对象标题；多条变化全部确认后事务提交，审核期间变化须重新审核。深色和全屏验收核对真实宿主主题标记与几何数据，不能只改测试文件名；弹窗底部确认按钮在窄屏实际可见。归档不移除已发生工时、费用或沟通的业务事实。参考任务见首批企业场景，仍沿本标准维护，不增设第二套开发标准。

Windows 浏览器测试与开发期截图统一通过 `scripts/browser-launch-options.mjs` 的 `safeChromiumOptions` 合并启动参数。Edge/Chrome 的全新临时配置可能触发本机空密码探测并累积账户锁定；已验证的规避方式是关闭 `AutofillAiWalletPrivatePasses`，同时保留 Playwright 原有默认参数。当前适配固定 Playwright 1.61.1 并核对实际运行文件摘要；升级工具链时须重新核对默认参数与账户事件后更新适配，不能删除核验或忽略全部默认参数。`scripts/browser-launch-options.test.mjs` 检查参数保留和入口覆盖，已接入测试总入口；这只改变开发测试，不改变业务包、账户密码或锁定策略。

1. 先读本标准和当前需要的契约；创建描述，确定身份、目标、范围与最小依赖。
2. 用原生文件/终端工具实现；先验证行为缺口，再修复。Windows 自动化使用 PowerShell 7。
3. beellix_develop check 只校验传入描述和清单；不读取工程，不执行代码，不声称构建或权限已通过。
4. 随入口包分发的 development/check.mjs 对实际工程做只读静态检查：显式打包白名单、入口、链接、私密文件、体积限制和输入摘要。通过原生终端运行，保持原生权限。输出仍不是测试或运行通过。
5. 实际构建、行为测试、语法检查、npm pack --dry-run 检查最终文件；再对最终 tarball 做隔离原生加载、调用与卸载测试。检查源码不等于检查 tarball，静态检查不执行迁移、构建或插件代码。
6. 回执记录标准、源码/锁文件/工具链及包摘要、真实测试项、未执行项。源码或包变化后对应证据失效。只打包不自动安装，明确授权后由 Beelli X 中台安装；禁止 plugin_manager install_bundle 安装 Beelli X 业务包到 Profile。
7. 安装、加载、业务初始化、可用、恢复验证分别验收。未交付的通用工程登记、模板生成、依赖协调和自动发布不写成已实现。收费授权与免费 MIT 按包明确，秘密和恢复密码不进代码、包、上下文或回执。

创造适配仅作用于首次启用本标准之后新建的原生 cordis 工作区会话；旧会话组成、记录、目录和业务数据不转换。不会强制改变用户的原生审批策略，也不新增可见模式。

## 7. 模型由插件声明，中台统一配置

插件在 package.json 的 beellixModels v1声明所需用途，字段以[模型接入](model-center.md)及当前公开类型为准：operation为chat、embedding、rerank或parse，kind为能力分类，required区分必需与可选；没有需求就不声明，不为插件自动加一套模型。

主对话、图片消息、原生模型选择、上下文压缩仍沿DSH。不仅凭厂商名称判断某型号是否支持图片，也不另加全局视觉中转链。chat用途可明确 default=host-main；embedding、rerank、parse不是主聊天模型，1.1.0静态检查拒绝它们冒用此默认值。独立连接由真实提供方实现，云API与本地方式按实际支持展示，不用演示连接冒充能力。

中台自动识别已安装包的声明：顶部一个插件一个标签，十项用途仍放在同一个标签；每个用途复用主模型卡片、图标、配置、详情和真实启停状态。kind用于筛选和能力校验，不把一个知识库拆成文档／检索／其他三个插件标签。Key只通过原生凭据服务保存，配置入口统一，状态／工具／回执不返回密钥。DeepSeek Search复用主连接的官方凭据引用，不增加重复Key输入，也不向自定义地址转发密钥。

专用模型提供方再次校验用途、修订、能力和启停；关闭保留连接和资料，取消不写入。需要上传资料的解析服务显式说明范围并由用户启用，默认路径以插件实际声明为准；不能把“已配Key”当作真实模型质量、费用或官方服务已经验收。

## 8. 安装、更新与恢复

用户从DSH原生入口只安装@beellix-ai/dsh-beellix-plugin；自有业务包通过Beelli X中台导入或npm／pnpm安装，落在自己的环境和registry，由原生Loader Include装配。停用入口也不能让业务包重新出现在原生市场；不靠DOM隐藏、全局接口过滤或卸载业务包实现。

更新服务地址由维护者在入口包的 src/update-distribution.mjs 统一预置，用户只检查和确认更新，不填写网站地址，不为每个业务包另建更新器。网站未建时为null，显示“更新服务尚未上线”，不访问假地址；旧用户源文件保留但不读取。[发布清单](public-plugin-distribution.md#网站未建设时的中台接入)只是接口，网站、账号、签名发行和受控下载未完成前不能宣称公网市场已上线。

检查只获取元数据；安装前锁定包名、版本、摘要和当前安装事实，核对兼容、来源、大小、归档及数据代次，再沿现有安装事务、备份与回退。数据代次变化未有专项迁移就阻断，不覆盖旧库；失败与待重启如实显示，不静默更新代码。正式公网发行须不可变并补齐可信签名及发布验证；同版不同摘要的本地候选只能显式导入，不能冒充新的公网正式版本。

开发标准、工程Schema、运行契约、插件版本和数据代次各自管理；本次标准1.1.0不改变现有插件0.1.1。免费UI入口为MIT，不把全部业务包自动改成MIT；依赖和原组件授权、商业许可分别核验。禁止把付费制品、客户资料或私钥写进公开目录。

## 9. 公众开发和共同交付

协作与收益沿[共创生态模式](../docs/ecosystem-model.md)，技术准入沿本节及E／G规则。接单任务补需求、承接修订、里程碑、成果许可与维护责任，关联在任务及交付回执，不新增运行清单字段。客户验收不自动公开代码、批准发行或完成付款；未确定费率和结算渠道时不生成收益承诺。

[生态适配与准入](ecosystem-conformance.md)规定发布者、兼容、工程、生命周期、中台、Agent、隐私、数据、模型、UI、质量和维护十二类要求，并按场景／工具／技能／能力／UI设置附加规则。适配到DSH、中台业务可用和市场可发行分别验收，不使用一个“兼容”标记代替全部证据。

Codex和DSH创造模式使用[同一任务及验收格式](plugin-development-task.md)：先确定需求、修改范围、契约基线、依赖和验收，再按实际工具开发。批量开发保持每包独立身份、隔离资料、需求覆盖和最终包回执；先验证代表性模板，不能用生成数量冒充完成数量。共享能力变更与插件开发分别协调，现用客户端和旧资料不因开发任务而自动获得修改授权。

当前index/read、描述校验和工程检查继续沿原实现；没有新增任务解析器、批量调度、全类型模板或自动发布。任务格式是可复用文档，不新增虚构工具名或清单字段。统一规范由随包快照按需分发，不把全部生态规范塞入每轮上下文；仓库、候选、已安装快照及真实采用各自记录。

## 10. 跨插件业务互通

当前仅本机主用户，沿DSH owner默认全权。新插件使用[本机主用户与数据访问](../docs/personal-data-permissions.md)和 `ctx.beellixData` 注册自己的业务资源；统一目录按需发现，不要求创建插件结对、人员角色或授权表。包名不是人的权限主体。多人身份接入前，不把负责人、会话ID或数据库角色当作用户。

独立业务库存储不等于业务孤岛；统一调用不共享表或直接SQL。业务插件负责对象关联、输入校验、审核、事务、幂等及可恢复事件；中台核验真实Agent、提供方启用状态、支持动作和真实账套，长任务和写入前重验。会话知识开关、任务范围和子代理执行约束保留。

旧结对SDK只兼容已有业务映射及文件，不推广为新接入目标；旧包权限策略不读取或迁移。后续真正引入多人身份时再扩展人的权限，并按I01—I12覆盖查询、汇总、导出和写入，不仅添加页面。此补充不改变v1安装清单或1.1.0标准号；data-platform主数据治理业务仍未交付。
