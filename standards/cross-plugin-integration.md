# 跨插件互通与授权标准

状态：2026-10-28 用户纠正总体方向：个人或企业部署均须提供全系统统一的数据访问与权限；不是让用户逐个配置插件之间的连接。下文已有的CRM／进销存结对契约仅作为旧兼容实现和审计依据，不再作为新插件接入目标。全系统能力尚未实现，不能把结对链路通过测试称作统一数据中台完成；实际状态见STATUS。

## 当前实现修订

当前仅本机主用户，默认全部授权，不增加插件授权或手工结对页面。当前契约以[本机主用户与数据访问](../docs/personal-data-permissions.md)为准；包名仅为调用来源。ctx.beellixData及原生beellix_data已有统一目录和访问实现，不需要另建data-platform包才能互通。本轮源码扩展的动作校验、原对象引用及企业模块准入见[企业业务模块](business-modules.md)。保留业务审核、独立数据库和知识任务范围。下文默认跨插件拒绝、结对管理及“只有结对实现”的描述为历史契约，旧接口仅兼容保留，不作为新接入目标。多人身份、字段权限和跨模块可靠写流程不据此视为完成。实际采用见STATUS。

## 当前有效的总体要求

1. 数据库插件提供公共存储、隔离实例和备份；数据中台承担全系统资源目录、主数据关联、数据服务和授权治理；业务插件登记自身数据与业务动作。个人、企业共用这一职责划分，身份与权限范围按部署扩展。
2. 安装并初始化业务插件后，其可用数据资源应登记到系统中台。业务插件、页面、知识检索及智能体经同一权限路径发现和访问资源，不要求用户先创建“CRM连接进销存”等结对连接。
3. 权限针对可信主体、插件身份、数据资源、动作、账套／组织、记录和字段。能发现、读取、使用、写入、导出、审核或过账分别受控；全系统可互通不表示所有用户或插件拥有全量访问权。
4. 独立物理库是存储与恢复边界，不是业务数据孤岛。资源读取走统一受控数据服务，业务写入仍交数据责任方执行规则及审核。已有独立库不因此合并，也不开放跨库管理员登录。
5. 客户、商品等系统主数据建立稳定身份与可追溯关联，兼容已有CRM及进销存实体。适配关系属于中台内部的数据治理；不能把同名记录自动合并，也不能让每个用户反复维护插件结对表单。

以上总体要求分阶段实施。当前可用API以personal-data-permissions及business-modules为准：统一资源入口已经实现，本机owner默认全权，独立库经责任方服务访问；企业多人／字段权限及通用可靠交付仍未实现。`packages/data-platform`尚不存在，也不是当前统一访问的必需依赖。保留旧库、旧授权、旧资料和既有合法单据；不按历史设想重复建设资源入口或包权限表。

以下章节记录已有兼容机制，其手工创建连接及结对授权不能再作为全系统目标设计。

## 1. 隔离存储，显式服务互通

应用各自拥有数据库、账套、附件和业务规则。互通走提供方公开的有界查询／业务命令，不能共享数据库登录、跨库JOIN、借用管理员连接、直接改对方表或强行挂载对方场景工具。数据中台可以承接已授权连接和数据加工，但安装数据中台本身不授予任何业务访问权，也不是所有应用互通的必选依赖。

中台维护已安装提供方、契约、连接、授权、撤销、健康及操作审计；业务提供方再次核验调用和对象权限。DSH保持执行、会话和原生审批；UI、模型、技能及子代理共用业务授权路径。购买资格、插件启用、负责人字段和场景绑定都不能替代跨应用授权。

当前同宿主插件属于可信本地代码，声明不是OS隔离。此标准限制正常接口调用，不能承诺防御恶意插件直接读取用户可访问文件／内存；开放不可信插件之前须独立完成运行隔离及威胁验证，不能靠隐藏连接参数宣称安全沙箱。

## 2. 通用互通规则

| 编号 | 要求 |
| --- | --- |
| I01 提供方和归属 | 注册须核对已安装包、真实来源、运行作用域、契约和features。稳定标识至少区分包／安装实例／账套／业务对象；模型传入的包名、ID或路径不构成身份。贡献冲突明确失败 |
| I02 可信执行身份 | 调用上下文由宿主连接或原生Agent链解析，保留原操作者、调用插件、父任务与委派范围；不能接受请求正文自报owner、管理员或用户ID。没有可信用户身份时只支持现有本机owner范围，不能伪造企业多人权限 |
| I03 默认拒绝与授权交集 | 放行条件为：有效连接∩调用者权限∩显式跨应用授权∩目标业务权限∩当前对象范围∩执行委派限制。未知动作、字段、账套、契约或失效服务默认拒绝；授予只读不隐含写入、导出、订阅、成本或财务权限 |
| I04 授权记录 | 绑定授权人、来源／目标安装实例与账套、操作、对象筛选、允许字段、用途、有效期、修订和状态。使用能实际执行的结构化筛选，不把自然语言当权限表达式；支持预览、撤销和必要的到期。跨企业连接须双方明确允许，默认不建立 |
| I05 字段及推导结果 | 服务端过滤记录及字段后再序列化，分页总数、汇总、搜索、导出、附件、事件和缓存使用同一权限。禁止靠UI隐藏成本、毛利、银行信息；派生汇总也不能泄漏被禁止字段。缺权限不能以0替代并伪报真实值 |
| I06 来源与映射 | 数据责任方明确；双方对象通过经确认的映射关联，显示来源、版本和同步状态。名称相同不自动合并；没有映射不猜测客户、商品或账套。历史单据保留交易时快照，不被后续客户改名或价目更新回写 |
| I07 有界业务命令 | 命令有输入输出、作用域、预期修订、幂等键、超时取消及可重试语义。禁止提供任意SQL、任意模型方法或任意文件路径；金融／库存过账等动作使用目标领域服务及其审批、期间、库存和余额校验 |
| I08 审核与副作用 | 开草稿、审批、过账、出库、收付款分别授权。模型辅助形成建议或草稿；人工确认绑定具体对象、内容摘要、账套及授权修订，提交前重新验证。上下文中的“confirmed”或同意文字不能跳过可信审核；子代理不取得业务写权 |
| I09 交付与一致性 | 一个提供方内用本地事务；跨应用采用可恢复步骤，不声称分布式原子提交。事件使用业务事务内outbox、持久化目标inbox及业务幂等；重试按至少一次交付设计，防止重复建单／收款，不承诺天然恰好一次 |
| I10 撤销和停用 | 每次调用、排队执行及长任务结果交付重新核验授权修订与服务状态。撤销取消在途／待执行操作，停止订阅、使受限缓存失效，不能继续使用旧令牌。此前已合法写入的业务记录按保留规则处理，不能承诺撤销能收回所有已导出副本 |
| I11 恢复和重新接回 | 映射、授权、outbox／inbox与检查点纳入备份策略。恢复新库产生新的实例代次，原授权及映射不能自动指向新副本；重新确认、对账再补发，避免旧事件向恢复副本重复写款或跨账套 |
| I12 审计和演进 | 记录原操作者／执行插件、源目标实例／账套、动作、授权修订、请求／关联ID、对象修订、结果及拒绝原因；不复制秘密和整份业务正文。事件／DTO／操作契约有版本、弃用和兼容测试；未知版本不强行解析 |

记录范围、字段投影和委派限制须在查询入口、业务写入及结果交付处实际执行。授权编辑和发布资格不等于授权者本身能访问目标数据，不能由调用方给自己加权。中台连接页以目标应用、共享内容、允许动作和停用开关呈现；技术ID、规则、期限和审计放详情，遵循[界面规范](../docs/design.md)。

## 3. CRM与进销存的数据责任

| 数据 | 责任方 | 跨应用处理 |
| --- | --- | --- |
| 线索、联系人、商机、跟进 | CRM | 进销存仅在授权下读取选定客户的必要建档信息；不默认获取私密跟进正文和全量联系方式 |
| 交易往来单位、开票／结算资料 | 进销存 | 可关联CRM客户，但交易主体、地址和结算信息独立确认；一个CRM关系对象不必等于一个法律／结算主体 |
| SKU、单位、仓库、可用量、价目 | 进销存 | CRM按范围查询；报价价目和实际成本分权，库存可用量带仓库、计量单位、时间及版本 |
| 商机转销售草稿 | CRM提出，进销存建单 | 映射客户和商品，核对单位／币种／价格后建立有来源的草稿；不自动审批、占库、出库或收款 |
| 履约与回款 | 进销存 | CRM接收授权订单的状态和必要汇总；原始财务流水、银行信息、供应商价和成本默认不共享 |
| 预计金额、成交金额、实际回款、实际毛利 | 各自业务对象 | 分别展示并保留来源；商机成交不等于发货／收款，销售订单预计毛利不等于已实现毛利 |

两库不建跨库外键；关联信息由版本化映射与服务核验维护。CRM可独立安装、进销存可独立安装；未安装另一应用时正常提供自身功能，只将互通入口显示为未连接。

第一条互通链：用户明确连接两个账套并选择共享范围→确认客户关联→CRM请求新建销售草稿→进销存核验授权与内容后返回草稿引用→用户在进销存审核和履约→授权状态投影返回CRM。创建失败保留请求结果可查询；结果丢失后按幂等键查询，不重新创建第二张订单。V1连接设计以本机owner为操作者，未来多人需先接可信主体及目标系统业务权限，不将CRM“负责人”直接当登录用户。

## 4. 记录和事件的最小信息

实施的DTO／事件至少表达：契约版本、提供包和安装实例、源账套、业务对象类型／ID／修订、唯一事件或请求ID、关联ID、原操作者引用、授权ID／修订、发生时间、允许字段载荷。时间戳不代替顺序号，业务对象ID不代替安装实例；状态更正、删除／归档、撤销和实例恢复均有明确语义。

这些是协议设计要求，不是现有beellixContract v1的新增字段。具体传输、可信上下文证明、原子outbox及重放策略须在隔离实现和测试后确定；不先搭无限通用事件总线或复制整库。第一版只实现所需动作与有界队列，保留失败、重试、冲突和人工对账入口。

## 5. 必须通过的互通验收

| 用例 | 必须观察到 |
| --- | --- |
| X01 未连接／无授权 | 读取、写入、导出、搜索、订阅都拒绝，不从旧缓存返回资料 |
| X02 身份、账套和对象伪造 | 更改正文中的用户、插件、账套、客户ID不扩大权限；其他实例相同对象ID不串用 |
| X03 字段和范围 | 销售只看授权客户与销售状态，成本／毛利／银行字段及其汇总不可见；财务权限单独开启 |
| X04 审核与重复请求 | 拒绝／取消无副作用，重试只建一张草稿，不重复扣库存、确认订单或登记收款 |
| X05 撤销、停用及长任务 | 进行中和队列中的旧授权失效，取消订阅，过时结果不再交付；已完成单据保留审计 |
| X06 网络／进程中断和乱序 | 中断后可接回，重复／迟到事件不覆盖新状态；恢复投递不导致重复业务写入 |
| X07 账套恢复与升级 | 新副本须重新确认，旧映射／授权不自动迁移；未知DTO版本明确阻断 |
| X08 多入口同权 | UI、DSH工具、技能、子代理、导出和后台任务遵守同一规则；单机owner不会被宣传为多人权限已完成 |

首次验收用两个隔离账套、至少两个互异授权范围及受限字段完成。只有契约和模拟用例时仍是设计／协议验证，不算真实CRM与进销存联调通过。

## 6. 当前接入状态

CRM原有工具继续通过真实场景绑定并对模型写入审核；本地HTTP只接受owner连接。新增公共互通服务由中台登记已安装提供方、验证目录、授权与映射；两侧独立提供方核对账套并处理本域规则，原service不借其他应用会话。CRM仅增加005-integration迁移、独立适配和crm_inventory工具，不替换原客户／商机业务。公共数据库仍不提供跨场景SQL，负责人／团队仍不是账号权限。

实际代码为shared/runtime/interoperability.mjs及其.d.ts、两包各自src/integration.mjs。源和目标各自读写自己的库；授权快照纳入库备份，CRM outbox与进销存业务幂等账簿负责中断恢复。迟到结果、撤销、子代理、字段投影、账套恢复和未知版本分别验收；证据见STATUS。插件原设置页不再提供管理动作，旧只读连接查询兼容；日常客户端采用与源码状态分别记录。

## 7. 中台统一管理与插件 SDK

管理权与使用权分开。本轮管理者为DSH原生连接认定的本机owner，不能从请求正文、CRM负责人或工具参数自报身份。中台HTTP `/beellix/console/integrations` 及全部子接口先验证原生连接和owner，写操作另需独立CSRF令牌。界面只有“连接／操作记录”，不新增虚构的用户、部门或角色。业务使用权由连接内的源／目标安装与账套、操作、映射及共享范围约束，owner也不能通过模型绕过业务审核。

`ctx.beellixInteroperability` 的公开对象只有 `contractVersion:1` 与 `register(provider)`。提供方注册后只拿到 `installationId`、`list(accountId)`、`call`、`review`、`dispose`；不能全局枚举授权、创建连接、编辑映射或启停别的连接。中台私有管理对象不注入业务插件。安装归属、真实目录和启用状态仍每次核对；这属于可信本地插件接口边界，不是防御恶意本机代码的OS隔离。

新增互通由目标数据插件登记 `contracts`，完整类型为 [interoperability.d.ts](../dev/shared/runtime/interoperability.d.ts)：

| 项目 | 必需约束 |
| --- | --- |
| 协议身份 | 稳定唯一id、可读title、source.packageName；target.packageName必须等于当前注册包，不能冒用现有协议 |
| 两侧账套 | 新协议固定 `sourceAccount`／`targetAccount`，来自提供方真实accounts列表；安装身份由中台生成，不接受正文自报 |
| 允许动作 | operations逐项声明id、title、effect=read或write；只读动作可default，写动作不默认授权。未知动作拒绝 |
| 配置字段 | fields使用mapping／single／multiple／checks；可读名称、允许集合、必需项和可选条件。中台按声明生成表单，不能提交函数、SQL或任意路径 |
| 资料选项 | provider.choices(accountId,{collection,q,offset,limit,ids})；只返回允许集合的id／name、真实total、nextOffset及selected名称，不返回完整业务正文；单页不超过100、所选ID不超过100 |
| 范围校验 | contract.validate检查权限范围和必需／额外字段，provider.validateGrant在各自数据库复核映射；无效应抛明确错误，不能静默取第一项 |
| 调用约束 | contract.authorize检查具体对象与参数，目标provider.call再次按本域权限和对象范围处理；工具入口由原生可信会话绑定确定调用账套和readOnly，子代理只读 |
| 返回投影 | contract.project只返回公共DTO、授权总数及汇总；不能依赖前端隐藏字段。不得返回成本等未授权推导值 |
| 写入审核 | write必须提供provider.preview（兼容previewDraft）和contract.review逐项说明；中台签名绑定原请求、安装、授权修订及目标状态，过期或修改映射后原审核不可再用 |
| 业务一致性 | source保存自己的投递意图，target在同一业务事务内保存requestId及结果；中台不替插件模拟跨库原子提交，重试不得重复业务写入 |
| 生命周期 | 停用立即阻断并取消在途结果；启用重新校验两侧账套与授权快照。恢复新库不得自动续接；未知协议时旧授权只展示不可用，可停用，不能扩大访问 |

中台私有API：GET `integrations`（目录与连接）、`integrations/choices`（受限分页选项）、`integrations/audit`（倒序分页）；POST `integrations/create`、`integrations/update`、`integrations/enabled`。编辑必须带expectedRevision，只能修改原两侧账套内的权限和映射；换账套须另建连接。发布快照失败后保持pending／停用，不能显示已成功启用。默认有效期一年，过期必须明确修改期限再重新启用；不删除历史单据。

旧CRM／进销存授权文件、ID和账套键保持原样，读取不触发迁移；其既有双向协议由兼容适配处理。新协议使用通用账套字段并从目标提供方登记，停用提供方即移除可执行适配，旧授权记录保留。通用注册与配置扩展不等于当前已经提供所有业务系统的适配器；具体插件必须完成I01—I12与X01—X08及实际业务验收。
